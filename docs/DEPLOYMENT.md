# Развёртывание и эксплуатация BarsikChat

## Требования

Для 100 пользователей рекомендуется минимум 2 CPU, 2 ГБ RAM и 20 ГБ SSD. Объём диска следует увеличить, если пользователи активно отправляют видео и архивы.

Потребуются:

- Linux-сервер либо постоянно включённый компьютер с Windows/macOS;
- Docker Engine или Docker Desktop с Compose;
- домен и HTTPS для установки PWA, камеры, микрофона и Web Push;
- открытый наружу reverse proxy либо туннель.

## Переменные окружения

Скопируйте `.env.example` в `.env`. Файл `.env` исключён из Git и Docker build context.

| Переменная | Назначение |
|---|---|
| `PORT` | Внутренний порт приложения, обычно `3000` |
| `POSTGRES_PASSWORD` | Обязательный уникальный пароль PostgreSQL |
| `DATABASE_URL` | Строка подключения; пароль должен совпадать с `POSTGRES_PASSWORD` |
| `APP_ORIGIN` | Точный внешний origin, например `https://chat.company.ru`, без пути |
| `SESSION_DAYS` | Срок действия сессии в днях |
| `MAX_USERS` | Максимальное число аккаунтов, по умолчанию 100 |
| `MAX_UPLOAD_MB` | Максимальный размер одного файла |
| `DATA_DIR` | Каталог вложений внутри контейнера |
| `VAPID_PUBLIC_KEY` | Публичный Web Push-ключ |
| `VAPID_PRIVATE_KEY` | Приватный Web Push-ключ |
| `VAPID_SUBJECT` | Контакт администратора в формате `mailto:` |

Если пароль содержит `@`, `:`, `/`, `#` или другие специальные символы, URL-кодируйте его внутри `DATABASE_URL`.

Сгенерировать VAPID-ключи:

```bash
docker run --rm node:22-alpine npx --yes web-push generate-vapid-keys
```

Не публикуйте `.env`, приватный VAPID-ключ и резервные копии.

## Локальный запуск

```bash
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:3000/api/health
```

Ожидаемый ответ: `{"status":"ok"}`. PostgreSQL наружу не публикуется, а приложение и встроенный gateway привязаны к loopback-интерфейсу.

## Постоянный production-домен

1. Создайте DNS-запись домена на сервер.
2. Укажите этот HTTPS-origin в `APP_ORIGIN`.
3. Разместите Caddy или Nginx перед `127.0.0.1:3000`.
4. Разрешите наружу только 80/443, не публикуйте 3000 и 5432.
5. Проверьте проксирование `/socket.io/` и лимит тела запроса не меньше `MAX_UPLOAD_MB`.

Пример Caddy находится в `deploy/Caddyfile.example`. Caddy автоматически получает TLS-сертификат для доступного домена.

## Публикация с домашнего компьютера

Для временного доступа можно направить Cloudflare Quick Tunnel на встроенный gateway:

```bash
cloudflared tunnel --url http://127.0.0.1:3001
```

Укажите полученный HTTPS-адрес в `APP_ORIGIN` и пересоздайте приложение:

```bash
docker compose up -d --force-recreate app
```

Quick Tunnel подходит для демонстрации, но его адрес меняется после перезапуска. Для постоянной эксплуатации используйте именованный туннель и собственный домен. Компьютер, Docker, туннель и интернет должны работать непрерывно.

## Регистрация пользователей

Кода приглашения нет. Зарегистрироваться может любой человек, получивший ссылку, пока количество аккаунтов меньше `MAX_USERS`. Для закрытой организации рекомендуется:

- не публиковать URL в открытых источниках;
- закончить регистрацию коллег в короткое согласованное время;
- следить за количеством пользователей;
- в будущем добавить административное подтверждение аккаунтов либо SSO.

Количество пользователей можно проверить без изменения данных:

```bash
docker compose exec postgres psql -U chatosnova -d chatosnova -c "SELECT count(*) AS users FROM users;"
```

## Обновление

Перед обновлением сделайте резервную копию.

```bash
git pull --ff-only
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:3000/api/health
```

Миграции применяются автоматически перед запуском HTTP-сервера. Клиентская PWA проверяет новую версию при возврате в приложение и периодически во время работы. Перезапуск единственного backend-контейнера даёт короткое переподключение WebSocket; для полностью безостановочного backend-обновления понадобится многорепличная схема и общий адаптер Socket.IO.

## Резервное копирование

Создавайте резервные копии PostgreSQL и тома вложений одновременно. Пример для каталога `backups`:

```bash
mkdir -p backups
docker compose exec -T postgres pg_dump -U chatosnova -d chatosnova --no-owner --clean --if-exists > backups/barsikchat.sql
docker run --rm -v chatosnova_chatosnova_data:/source:ro -v "$PWD/backups:/backup" alpine tar czf /backup/barsikchat-files.tgz -C /source .
```

Имя Docker volume зависит от имени Compose-проекта. Узнать его можно через `docker volume ls` или `docker inspect chatosnova-app-1`.

Храните копии на другом физическом устройстве либо в объектном хранилище. Шифруйте архивы резервных копий и регулярно проверяйте восстановление на отдельном тестовом сервере.

## Восстановление

Восстановление заменяет текущие данные. Выполняйте его только после дополнительной копии и проверки имён контейнеров/томов.

1. Остановите `app` и `gateway`.
2. Восстановите PostgreSQL из `barsikchat.sql`.
3. Восстановите содержимое тома вложений из `barsikchat-files.tgz`.
4. Запустите Compose и проверьте `/api/health`, вход, чат и скачивание файла.

## Мониторинг

```bash
docker compose ps
docker compose logs --tail=200 app
docker compose logs -f app
docker stats
```

Контролируйте:

- состояние health-check;
- свободное место на диске;
- рост таблиц `messages`, `attachments` и `sessions`;
- ошибки PostgreSQL, Web Push и миграций;
- срок TLS-сертификата и доступность домена;
- успешность ежедневных резервных копий.

## Аварийная диагностика

- `401` — отсутствует или истекла сессия;
- `403 Недопустимый источник` — `APP_ORIGIN` не совпадает с фактическим адресом;
- не подключается WebSocket — proxy не пропускает upgrade или указан неверный origin;
- не устанавливается PWA — нет HTTPS либо браузер не поддерживает установку;
- нет push — отсутствуют VAPID-ключи, разрешение браузера или HTTPS;
- `413` — лимит reverse proxy ниже `MAX_UPLOAD_MB`;
- приложение не стартует — сначала смотрите `docker compose logs app` и состояние PostgreSQL.
